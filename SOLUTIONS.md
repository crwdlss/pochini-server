Для каждой задачи: что сломано → как найти → как исправить → что спросят на собеседовании.

## 01 — Nginx не запускается

**Что сломано:** в `/etc/nginx/sites-available/default` после `listen 80 default_server` нет `;`.

**Как найти:**
```bash
ps aux | grep nginx     # nginx не запущен
nginx -t                # покажет: invalid parameter "root" ... line 3
```
Ошибка указывает на строку 3, а виновата строка 2: без `;` nginx склеил две строки в одну директиву.

**Исправление:** добавить `;`, потом `nginx -t && nginx`.

**На собеседовании:** «Как безопасно применить изменения конфига nginx?» → `nginx -t`, затем `nginx -s reload` (или `systemctl reload nginx`): reload не рвёт текущие соединения, в отличие от restart.

## 02 — 403 Forbidden

**Что сломано:** рабочие процессы nginx работают от `www-data`, а у файла права `600`, у папки `700`, владелец root.

**Как найти:**
```bash
tail /var/log/nginx/error.log          # Permission denied
ps aux | grep nginx                    # worker process — пользователь www-data
ls -ld /var/www/html; ls -l /var/www/html
```

**Исправление:** `chmod 755 /var/www/html && chmod 644 /var/www/html/index.html`

**На собеседовании:** «Зачем папке право `x`?» → для папки `x` значит «можно войти и обращаться к файлам внутри». Без него файл не прочитать, даже если у самого файла есть `r`. И почему `777` плохо: любой пользователь системы сможет подменить сайт.

## 03 — Кончилось место на диске

**Что сломано:** 18 МБ старого debug-лога в скрытой папке `/data/app/logs/.archive/`.

**Как найти:**
```bash
df -h /data                          # 100%
du -sh /data/app/logs/*              # почти пусто: * не видит скрытые файлы!
du -ah /data | sort -h | tail        # вот он
```

**Исправление:** `rm /data/app/logs/.archive/debug-2024-full.log` (и `filler.tmp` тоже можно).

**На собеседовании:** «Диск заполнен, твои действия?» → `df -h` (какой раздел) → `du` по уровням (что занимает) → удалить или заархивировать старое → настроить ротацию логов (`logrotate`), чтобы это не повторилось. Последний шаг — самый важный.

## 04 — Порт занят

**Что сломано:** на 8080 висит забытый `old-dashboard`.

**Как найти:**
```bash
cat /var/log/app.log         # Address already in use
ss -tlnp | grep 8080         # кто слушает порт и его pid
ps -fp <pid>
```

**Исправление:** `kill <pid>`, затем `start-app`.

**На собеседовании:** «Разница между `kill` и `kill -9`?» → `kill` шлёт SIGTERM: процесс может корректно завершиться, закрыть файлы и соединения. `-9` (SIGKILL) убивает мгновенно и без уборки. Это крайняя мера.

## 05 — Скрипт не запускается

**Что сломано:** две вещи: нет права на исполнение, и переводы строк Windows (`\r\n`).

**Как найти:**
```bash
ls -l /opt/scripts/backup.sh     # -rw-r--r-- : нет x
cat -A /opt/scripts/backup.sh    # ^M$ в конце строк
```

**Исправление:**
```bash
chmod +x /opt/scripts/backup.sh
sed -i 's/\r$//' /opt/scripts/backup.sh
```

**На собеседовании:** «Что такое shebang?» → первая строка `#!/bin/bash` говорит системе, каким интерпретатором выполнять файл. С `\r` система ищет программу `/bin/bash\r`, а её не существует. Отсюда ошибка `bad interpreter`.

## 06 — Приложение не видит бэкенд

**Что сломано:** в `/etc/hosts` для `backend.local` прописан старый IP `10.255.255.1`, а бэкенд работает на `127.0.0.1`.

**Как найти:**
```bash
ss -tlnp                         # бэкенд слушает 127.0.0.1:8000
curl http://127.0.0.1:8000       # по IP работает → проблема в имени
getent hosts backend.local       # 10.255.255.1 — вот оно
```
Ловушка: `dig backend.local` и `nslookup` спрашивают DNS-сервер и **не смотрят** в `/etc/hosts`. А программы (curl, браузер, приложения) смотрят. Поэтому для проверки «как резолвит система» нужен `getent`.

**Исправление:** заменить строку на `127.0.0.1 backend.local` (через nano: `sed -i` в Docker на `/etc/hosts` не работает). Просто дописать вторую строку мало: старая останется, и половина запросов уйдёт в никуда.

**На собеседовании:** «В каком порядке Linux резолвит имена?» → по `/etc/nsswitch.conf`, обычно сначала `files` (`/etc/hosts`), потом `dns`.

## 07 — Процессор загружен на 100%

**Что сломано:** `backup-helper` крутит бесконечный цикл, а «сторож» `sys-monitor` перезапускает его каждые 3 секунды.

**Как найти:**
```bash
top                                  # backup-helper — 100% CPU
kill <pid>; sleep 5; top             # вернулся!
ps -o pid,ppid,cmd -p <pid>          # кто родитель?
pstree -p                            # sys-monitor → backup-helper
```

**Исправление:** сначала убить родителя (`sys-monitor`), потом `backup-helper`.

**На собеседовании:** «Процесс воскресает после kill, почему?» → его перезапускает родитель, systemd (`Restart=always`), cron или supervisor. Правильно остановить через того, кто им управляет (`systemctl stop`), а не воевать с kill.

## 08 — Cron молча не делает бэкап

**Что сломано:** `backup-now` лежит в `/opt/tools/bin`. Этот путь добавлен в PATH только для интерактивного входа (`/etc/profile.d/`). У cron свой минимальный PATH: `/usr/bin:/bin`. Вывод задачи никуда не пишется, поэтому ошибку не видно.

**Как найти:**
```bash
# 1. заставить задачу говорить — дописать в /etc/cron.d/backup:
* * * * * root backup-now >> /var/log/backup.log 2>&1
# 2. через минуту:
cat /var/log/backup.log          # backup-now: not found
which backup-now                 # /opt/tools/bin/backup-now
```

**Исправление:** полный путь в cron-файле: `* * * * * root /opt/tools/bin/backup-now >> /var/log/backup.log 2>&1`

**На собеседовании:** «Скрипт работает руками, но не из cron, почему?» → другое окружение: PATH, переменные, рабочая папка, пользователь. Решение: полные пути, явный PATH в crontab и всегда логировать вывод.

## 09 — Диск полный, но файлов нет

**Что сломано:** лог удалили через `rm`, но процесс `log-writer` держит его открытым. Пока файл открыт хоть одним процессом, место не освобождается: `rm` удаляет только имя файла.

**Как найти:**
```bash
df -h /data; du -sh /data        # df: полно, du: пусто
lsof +L1                         # или: lsof | grep deleted
ls -l /proc/<pid>/fd/            # 3 -> /data/logs/service.log (deleted)
```

**Исправление (не убивая процесс):** `: > /proc/<pid>/fd/3`

**На собеседовании:** это классический вопрос «df и du показывают разное, почему?». Ответ: удалённые, но открытые файлы. Как не допускать: ротация логов через `logrotate` с `copytruncate` или с сигналом приложению переоткрыть лог.

## 10 — 502 Bad Gateway

**Что сломано:** две вещи.
1. В `/etc/api.env` написано `API_PORT=5001` без `export`. `source` создаёт переменную только в текущем shell, дочерний python её не видит → `KeyError` → API падает. А `start-api` всё равно пишет «запущен».
2. nginx проксирует на порт `5000`, а API должен слушать `5001`.

**Как найти:**
```bash
tail /var/log/nginx/error.log    # connect() failed (111: Connection refused) ... 127.0.0.1:5000
ss -tlnp                         # на 5000 и 5001 никого
ps aux | grep api                # API не запущен
cat /var/log/api.log             # KeyError: 'API_PORT'
```

**Исправление:**
```bash
sed -i 's/^API_PORT/export API_PORT/' /etc/api.env
start-api
# в /etc/nginx/sites-available/default: proxy_pass http://127.0.0.1:5001;
nginx -t && nginx -s reload
```

**На собеседовании:** «Разница между 502 и 504?» → 502 Bad Gateway: прокси не смог получить ответ от бэкенда (не запущен, отказ в соединении). 504 Gateway Timeout: бэкенд есть, но не ответил вовремя. Плюс главный урок задачи: никогда не верь сообщению «запущено», проверяй (`ss`, `curl`, логи).
